# iPadn 2.1.0 (32)：应用查询响应处理与诊断

## 真机证据与定位边界

用户报告 b31 / iOS 16.3.1 点击「检查连接」提示无法读取设备应用信息。日志中第一次未找到 VPN 接口；后续六次已通过 utun9#33、10.7.1.1 连通 62078 和 installation_proxy 动态端口，随后失败在 lookup。此时已走过配对会话及服务启动，不能把后续失败重新归因为未配对或单凭第一条日志要求重配对。

b31 的日志只记录 lookup 阶段，没有保留查询响应分类，因此尚不能确定这次设备返回的是错误、完成但缺少结果，还是读写异常。不要把本机测试当作已确认这台设备的根因。

## 改动

原查询代码只读取一条 plist 响应，并立即要求存在 LookupResult。对比 libimobiledevice 的 installation_proxy 查询处理，Lookup 是持续接收状态直到完成的命令。因此设备先返回状态、再返回结果时，旧实现可能把正常的中间响应误判为失败。

b32 将「检查连接」及应用列表的 Lookup 接收改为：

- 保持原有 Command、ClientOptions、ReturnAttributes 请求；不通过删除元数据属性规避错误。
- 接收状态并累积结果，直到 Complete；保留原有无 Status 的单次结果响应兼容性。
- 完成却没有有效结果、错误响应、畸形响应仍报错，不把查询失败伪装成「未安装」。分批结果后收到错误同样失败。
- 使用原有整体 30 秒查询超时，并限制最多 128 个响应、累计最多 64 MiB。不会无限等候或无限分配内存。
- 诊断记录发送、读取头部、读取正文、响应次数、固定状态分类及是否存在结果字典；设备错误映射为允许列表类别。任何任意 ErrorDescription、应用标识、应用列表、购买记录、证书或私钥都不进入这些日志。
- 提示能区分要求解锁、缺少结果、socket / 响应错误等；诊断首行显示 2.1.0 (32)。

b29 的配对格式、StartSession、TLS provider、VPN 选择和 IP_BOUND_IF、服务端口连接、安装上传与购买记录核验逻辑保持不变。legacy.rs 只添加一段写入诊断的方法，去掉该方法即与原文件逐字一致。未引入 b30 的 TLS 替换；依赖清单与锁文件不变。基准核对结果随日志交付。
